# PL-0007 — Web Capability Archaeology and Consolidation

Status: CAPTURED
Classification: Riverview Internal
Category: Web / Operator Capability / Architecture
Priority: Strategic
Originator: Steward
Date Captured: 2026-08-26

## Idea

Perform a future read-only archaeology of existing Estate/Riverview web surfaces
as capability artifacts before any consolidation, replacement, or redesign.
Start with the Office of the Steward, then separately inventory the current
Riverview operator interface, Spatial interface/site, DNAS, and other surfaces
discovered from canonical documentation.

## Future inventory

Record operational capabilities, controls, dashboards, workflows, launch
conventions, notifications, resource controls, resident/operator interactions,
useful existing behavior, obsolete behavior, duplication, generic Hermes
capabilities, and capabilities that must remain Riverview institutional
authority.

The objective is capability preservation, not HTML scraping or automatic
replacement.

## Boundaries

Hermes may be a replaceable execution substrate for a future bounded package.
It does not own institutional meaning, resident identity, authority, canonical
state, notification acceptance, or lifecycle acceptance. No web inspection,
consolidation, or implementation is authorized by this parking item.

## Promotion condition

Promote only with an explicit Steward-committed inventory scope, preservation
criteria, authoritative surface list, regression basis, and acceptance boundary.

## Required future operator capability inventory

The archaeology must identify the capabilities needed for a unified Riverview
Resource & Work Command Center. This is a dense, mining-dashboard-style
operational view, not a copy of mining software. At a glance it should answer:
what is running, waiting, broken, needs the Steward, what resources are
available, and what is consuming capacity.

Inventory requirements include dynamic Codex seats (including C1/C2/C3), fuel
and capacity observations with freshness, current workload, proven credential
and resource correspondence, local GPU/node state, model and VRAM/utilization/
thermal/power data where available, reservations, allocation, SSH/WOL and
power-management capability, and future local/external providers. Also inventory
Hermes run state, tranche/package, provider/model, context and turn/run budget,
workers/processes, stage, activity/heartbeat, blocker, Steward-attention state,
and last notification state. Campaign Runner fields must include objective,
package, work order, role, attempt, repair generation, candidate/basis,
validation, lifecycle, worker/resource, and stale/fence state. Grace-facing
views must retain contracts, priorities, pending decisions, Engineering waits,
validation waits, and acceptance waits.

This requirement is future archaeology and preservation work only. It does not
authorize UI implementation or replacement of existing Office capability.
