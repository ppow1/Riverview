# RV-018.6 character development and resident parity evidence

## Estate capability audit

The Estate source set shows a real bounded resident gateway and multi-resident
room lifecycle. `src/estate/core/resident_gateway.py` resolves named resident
models, session identity, attachments, provider routing, and bounded interaction.
`src/estate/core/multi_resident_room.py` and
`src/estate/core/conference_room_lifecycle.py` implement participant lifecycle,
speaker identity, filtered context, turn planning, and authority-preserving
room state. The targeted Estate regression set covering these paths passed 30
tests on 2026-08-15.

Character state is deliberately broader than a runtime prompt. The Estate
`docs/character-architecture/Character_Card_Template_v0_1.md` defines identity,
office, authority, boundaries, communication style, traits, memory sources,
provenance, and export boundaries. `character_continuity.py` keeps versioned
cycles and continuity artifacts; `resident_memory_runtime.py` keeps proposed
memory separate from approved durable memory and preserves evidence, review,
classification, and audit lineage. This is **ESTATE_REAL_WORKING** for the
bounded gateway/room and governed continuity mechanisms, with character-card
authoring represented as **ESTATE_PARTIAL** where the source set supplies the
governed artifact/template but not one unified browser authoring surface.

## Riverview implementation

Riverview now has a separate `CharacterDesignerWorkflow` and `CharacterStore`.
Accepted resident definitions are versioned (`v1`, `v2`, ...), retain the prior
version, author, source evidence, rationale, reviewer, timestamp, classification,
and review state. Proposals can be accepted, rejected, or left unresolved;
only an accepted proposal can publish a new runtime version. Grace's operational
authority is not part of character state and remains enforced by the existing
seed/objective promotion boundary.

`ContinuityStore` separates session history and candidate continuity from
published accepted continuity. Runtime sessions consume only accepted character
versions and accepted continuity references. Conversation text cannot rewrite
canon automatically.

`ResidentConversationGateway` exposes the version and continuity references in
the typed resident metadata and adds them to provider context references. Its
bounded `room_chat` executes one ordered provider round for the admitted
participants, preserving speaker identity, character version, correlation, and
the no-authority-expansion invariant. It does not recurse resident turns.

The browser operator consumes the same gateway for resident selection and room
conversation. No interface owns a duplicate character definition. SillyTavern
continues to be an adapter-level path; it is not a second canon store.

## Acceptance evidence

Automated acceptance covers:

- Helen/Alfred/Ingrid identity and character-version separation;
- rejected proposals remaining outside current canon;
- accepted proposal publication with prior-version lineage;
- candidate continuity remaining unavailable until governed publication;
- ordered provider-generated room responses with each participant identity;
- no resident role or room context confers operational authority.

The live browser operator already proves real text, local microphone/STT, and
reference-only artifact interaction. This package adds the machine-verifiable
authoring/versioning and room-provider evidence. A fresh human browser run for
resident switching and room response visibility remains experiential evidence,
not something to claim from unit tests alone.
