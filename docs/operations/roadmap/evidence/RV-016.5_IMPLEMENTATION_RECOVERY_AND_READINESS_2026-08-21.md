# RV-016.5 implementation recovery and readiness — 2026-08-21

## Decision boundary

RV-016.5 is not complete. The checked-in roadmap remains `pending`, and RV-016
remains `pending` because its final child acceptance is open. This document
recovers the implementation and evidence state; it does not change roadmap
status, runtime services, acceptance state, or implementation code.

## Recovered implementation paths

The current implementation is a bounded reference/model layer plus a small
browser surface:

| Concern | Exact path | Recovered behavior |
|---|---|---|
| Spatial entities and projection | `src/riverview/spatial/model.py` | Immutable entities with closed states (`KNOWN`, `PROPOSED`, `UNKNOWN`, `CONFIGURATION_DERIVED`) and provenance; projection has no execution/control method. |
| Avatar binding | `src/riverview/spatial/avatar.py` | Reference-only binding of resident identity, asset reference, classification, and resident provenance; it does not render an avatar. |
| Status projection | `src/riverview/spatial/status.py` | Frozen, read-only tuples for services, diagnostics, objectives, and capacity. |
| Input mapping | `src/riverview/spatial/input_mapping.py` | Typed `voice`, `controller`, `gaze`, or `hand` input; `shutdown`, `power_off`, and `retire` require confirmation. This maps values; it does not integrate a device. |
| Browser/WebXR prototype | `src/riverview/spatial/prototype.py` | Inline HTML canvas logical-room scene, proposed labels, `navigator.xr`/`immersive-vr` session attempt, and disabled operational controls. |
| Loopback route | `src/riverview/operator/openwebui.py` | Authenticated operator service serves the prototype at `/spatial`; `/health` is separate. |
| Private-LAN preparation | `src/riverview/operator/lan_spatial.py`, `src/riverview/operator/lan_spatial_service.py` | TLS listener intended to expose only `/spatial` and `/health`; default preparation target is `192.168.1.88:18443`, with a short-lived certificate under `A:\Riverview\runtime\operator\tls`. |

The LAN listener rejects loopback binding, requires TLS 1.2 or newer, suppresses
request logging, and returns `404` for other paths. It is a bounded read-only
surface, not a Quest runtime or a control channel.

## Why the waypoint was reopened

The earlier RV-016.5 completion was machine-only and treated backend/model
evidence as if it proved the human experiential gate. The subsequent factual
audit and `RIV-SPAT-0004` correction preserved that transition historically and
corrected the current state from `completed` to `pending`. The 2026-08-20
roadmap reconciliation records the reason explicitly: the implementation is a
Python model/prototype, while real Quest, headset, frame/comfort, and
end-to-end experiential evidence remain absent.

This is a recovery of an evidence mismatch, not a request to erase history or
to reinterpret the existing machine result. The governing distinction is:

- `MACHINE_ACCEPTANCE`: contracts, projections, synthetic inputs, and backend
  timing;
- `STEWARD_EXPERIENTIAL_ACCEPTANCE`: a rendered runtime, device/user-visible
  operation, physical input, frame timing, reconnect/degraded trials, and
  explicit Steward judgment.

## Launch and runtime behavior

The currently launchable behavior is the Riverview operator service's
loopback `/spatial` page. It draws a logical room marked `PROPOSED`, identifies
resident references as read-only, and states that operational ownership stays
with PostgreSQL/Riverview. The Enter button attempts `immersive-vr` only when
the browser exposes `navigator.xr`; otherwise it reports WebXR unavailable. A
successful browser session changes only page text to indicate that the WebXR
session is active; operational controls remain disabled. Session end and
request failure are reported in page text.

The optional LAN preparation serves the same page over HTTPS and exposes only
`/health` and `/spatial`. It does not expose chat, database, shell, provider,
or control endpoints. WebXR still depends on a Quest browser trusting the
certificate and establishing an actual immersive session. No public exposure
is authorized by this evidence.

## Telemetry and instrumentation recovered

There is one measured machine result: 1,000 projection/input iterations over
100 spatial entities completed in `1.097 ms` on the acceptance host, with stable
entity count and confirmation required for the destructive gesture. This is
backend projection/input-loop timing only. It is not render frame time, FPS,
motion-to-photon latency, user-visible input latency, transcription latency,
model first-token latency, comfort, or presence.

The current prototype and LAN listener do not instrument or persist headset
identity, OpenXR runtime identity, controller/hand/gaze/head-pose samples,
frame timing, dropped frames, reconnect duration, degraded-mode behavior, or
human comfort observations. No physical Quest session, microphone, controller,
hand-tracking, gaze, or head-pose trial is evidenced.

## Physical Quest/OpenXR gaps

The following are acceptance blockers, not merely optimization opportunities:

- no rendered 3D application with a real resident avatar;
- no Unity, Unreal, native OpenXR, or Quest-compatible packaged runtime;
- no connected or exercised Meta Quest device and no runtime/device identity;
- no physical controller, hand, gaze, head-pose, or microphone input path;
- no render FPS/frame-time or dropped-frame evidence;
- no end-to-end user-visible input, transcription, or model first-token latency;
- no reconnect or degraded-operation trial;
- no comfort/presence observation and no explicit Pat/Steward accept/reject
  decision for the actual rendered session.

The `1.097 ms` result, passing Python tests, `/spatial` availability, and LAN
TLS preparation therefore remain implementation/readiness evidence only.

## Smallest follow-on engineering package for physical acceptance

The minimum bounded package should create one disposable, read-only physical
acceptance slice without widening Riverview authority:

1. **Runtime slice:** package the existing logical scene and one
   provenance-bound resident avatar into a Quest-runnable WebXR/OpenXR-capable
   build, retaining the existing read-only ownership and confirmation rules.
2. **Device path:** establish a trusted private-LAN HTTPS path, record Quest and
   browser/OpenXR runtime identities, and prove only `/health` and `/spatial`
   are reachable from the device.
3. **Instrumentation:** capture bounded session metadata, frame time/FPS,
   dropped frames, input-to-visible timing, reconnect timing, and degraded-mode
   outcome; keep payloads and sensitive asset content out of telemetry.
4. **Acceptance drill:** run representative controller, gaze/hand (if
   supported), and voice/microphone cases; include a safe confirmation test,
   disconnect/reconnect, and degraded operation. Record the exact artifact,
   device/runtime identity, measurements, and observed failures.
5. **Steward gate:** obtain explicit Pat/Steward comfort and responsiveness
   acceptance for that physical session. Promote RV-016.5 only if every
   machine and experiential criterion is evidenced; otherwise retain `pending`
   with the failure and recovery path recorded.

This package is the smallest path to real physical acceptance because it
supplies the currently missing rendered runtime, device, instrumentation,
recovery evidence, and human gate while preserving the existing authority and
read-only boundaries.
