### Why the mirror evolved

The original uncropped scrcpy output showed both Quest eyes side-by-side. This was useful for proving live framebuffer movement but was not a convenient left-eye acceptance view.

An early assumed crop, `--crop=1832:1920:0:0`, was wrong and clipped the left-eye view severely. The uncropped Quest framebuffer was observed at approximately `1920 x 1396`, with a stereo composition; crop coordinates must be derived from a current uncropped capture rather than guessed.

The current script uses the final tested configuration `--crop=9000:8000:0:0`. It was accepted as useful enough for left-eye Quest acceptance, but the crop is a diagnostic presentation choice, not a change to Quest stereo rendering. It may include black border and should not be treated as exact optical lens geometry.

### Awake/watchdog behavior

`settings get global stay_on_while_plugged_in` returned `15` during the investigation. That setting alone was insufficient: the Quest could still sleep/blank through wear/proximity and normal headset behavior, causing scrcpy to mirror a black display.

The practical session protection is the combination of:

- `KEYCODE_WAKEUP` before launch and periodically while mirroring;
- scrcpy `--keep-active`;
- scrcpy `--disable-screensaver`;
- scrcpy `--screen-off-timeout=86400`;
- scrcpy `--stay-awake`;
- keeping the headset awake and the scrcpy process in an interactive session.

The current launcher does not permanently write Android settings. Its screen/activity controls are scrcpy session arguments and the wake keyevent is reversible. If a future diagnostic manually changes a persistent Android timeout, capture the original first:

```powershell

```

Restore the captured value explicitly after the session:

```powershell

```

Do not delete or overwrite settings without first recording the current value. A stronger charger/cable is a physical power issue, not an ADB setting repair.

## Chronology and diagnostic lessons

### Initial desktop room and generated GLB

The first Spatial implementation was a desktop/browser raw WebGL room. It loaded the generated GLB through `/spatial-assets/evelyn-test.glb`. The model initially appeared too large/close, so its desktop transform was bounded to an upright human-scale placement near `(0, 0.80, -2.20)` with scale `0.62`.

Pat accepted a temporary FRONT/LEFT/REAR/RIGHT desktop inspection control as proof that the asset was real 3D geometry. Distinct rendered captures from the same object changed across those rotations. Those controls are diagnostic desktop controls, not Quest locomotion.

### Desktop versus immersive confusion

Desktop rendering was not proof of immersive rendering. The browser scene and the immersive WebXR path were separate execution paths even though they shared some source helpers. Early immersive entry showed a starfield/dark environment and did not show the desktop room or desktop GLB. The important lesson is to inspect the actual `requestSession('immersive-vr')` render loop and the physical Quest framebuffer, not the desktop scene graph.

### Input/teleport diagnostic phase

Several early builds claimed that pointing at the floor and pinching a green marker would teleport. Pat physically observed no marker and no usable teleport. A visible XR input diagnostic panel was added to expose `inputSources`, handedness, target-ray mode/spaces, joints, poses, floor rejection, marker state, select events, and squeeze events. This remains an unresolved investigation because the physical input values were not yet turned into an accepted locomotion path.

Do not assume that a Quest hand has a useful `targetRaySpace`, that a pinch becomes `select`, or that a controller-style ray is available. Capture actual `XRInputSource` values first. A broad select-to-exit behavior also conflicts with a future deliberate teleport/select gesture and must be replaced with a dedicated exit design.

### Deployment/cache uncertainty

Pat repeatedly saw an unchanged Quest page after code changes. This was not safely diagnosable from source or HTTP status. The visible build stamp, generated deployment timestamp/token, `/spatial-build` endpoint, no-store response headers, and one-refresh procedure were introduced to close that ambiguity. This deployment identity is now part of the acceptance process.

### Minimal XR bisection

The immersive renderer was reduced to a blue clear color and one magenta cube. Pat physically confirmed that the Quest session, local-floor reference space, XR framebuffer, stereo output, and basic primitive draw were functional. That minimal build was the foundation for subsequent bisection and should not be reopened without regression evidence.

### Right-eye-only room failure and stereo repair

The next room-only build showed room geometry in the RIGHT eye while the LEFT eye was effectively black. This isolated a per-eye rendering defect rather than a room-geometry failure. The repair preserved per-eye `XRView` handling, used `layer.getViewport(view)` and the view’s own projection/inverse transform, disabled stale scissor state, and moved framebuffer color/depth clearing outside the per-eye loop so the second eye did not erase the first. Green LEFT and magenta RIGHT diagnostic markers were used. Pat physically observed room geometry and both markers in both eyes.

Future work must preserve:

- one XR framebuffer bind per frame;
- one clear per frame before the view loop;
- a separate viewport for every `XRView`;
- the `XRView.eye` value rather than assuming array order;
- that view’s projection and inverse transform;
- per-eye WebGL error checks.

### Immersive GLB insertion

After stereo was accepted, the existing generated GLB was added to the room-only immersive branch without changing the source asset. The physical result reported by Pat was that the room and generated GLB were visible in immersive WebXR. This proves the GLB can exist in the actual immersive room, not merely in the desktop renderer. GLB visual quality, background reconstruction artifacts, and production character quality were intentionally not addressed.

### Power limitation and current pause

The cable used during ADB/scrcpy debugging extended operating time but did not maintain Quest battery charge indefinitely. The headset battery eventually depleted during XR testing and is currently being charged from a stronger charger. Do not claim a specific charger or cable electrical capability unless it has been measured. Check headset battery/power state before starting a long physical acceptance sequence.
